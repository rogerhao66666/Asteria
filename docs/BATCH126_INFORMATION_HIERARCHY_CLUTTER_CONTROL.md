# Batch 126 — Battle Information Hierarchy / Clutter Control

Batch 126 formalizes the presentation rule that gameplay complexity must not
become visual complexity.

Information can be authored/projected as:
- persistent
- contextual
- focused
- compact
- hidden
- overflow

Stress validation covers seven resources, twelve statuses, twelve party members,
eighteen timeline entries, and a boss + adds + summon information mix.

A large roster is not handled by endlessly shrinking the same card. It moves
through primary detail, compact representation, then overflow while preserving
the focused member in the primary group.

Resources and statuses use priority plus context. A project may keep Vitality
persistent, Momentum compact, Rage contextual, and a detailed Resolve meter
focused-only. The engine does not attach semantics to those names.

Design reference policy:
Asteria may learn from polished JRPG interfaces, including commercial party JRPGs'
clarity, focus hierarchy, command readability, and interaction rhythm. This is a
quality/design reference only. Asteria must remain generic, adaptive and
project-configurable, and must not copy or hardcode reference-game-specific mechanics,
party assumptions, resource taxonomy, command structure, or exact layout.

Product rule: the lower layer preserves creative freedom; the presentation layer
organizes that complexity for the player.
